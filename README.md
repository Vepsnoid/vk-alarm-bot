# VK Alarm Bot — мониторинг VK и форвард в Max

Сервис следит за пабликами VK и публикует **свежие** посты в каналы мессенджера **Max** по расписанию: с фильтрами, обработкой промптом ИИ, копированием медиа, журналом проверок и событиями.

## Возможности

- **Потоки**: список источников VK (ссылки `vk.com`/`vk.ru`, короткие имена, `club123`/`public123`/`id123`, `wall-1_2`) → каналы Max, у каждого потока свой интервал проверки.
- **Курсоры по источникам**: для каждого источника запоминается последний id поста, поэтому при следующей проверке забираются только новые посты.
- **Повтор при сбое отправки**: доставка подтверждается по каждому каналу отдельно. Если Max ответил сетевой ошибкой/5xx/429, пост остаётся в очереди (статус «В очереди (повтор)») и досылается в следующих проверках — при этом повтор уходит только тем каналам, которые действительно не получили сообщение (остальные не дублируются). Неверный токен или канал (4xx) повторять бессмысленно: такой канал просто фиксируется в ошибке события. После нескольких неудачных попыток пост помечается `failed` с причиной. Гарантия — «доставим хотя бы раз»: если процесс упадёт между отправкой и записью результата, канал может получить пост повторно (лучше дубль, чем потеря).
- **Всплеск публикаций**: за одну проверку обрабатывается до `MAX_NEW_POSTS_PER_RUN` (по умолчанию 200) новых постов на источник; если новостей больше, в журнал и колокольчик попадает предупреждение о пропущенных самых старых постах (уменьшите интервал проверки потока или поднимите лимит в `.env`).
- **Секреты в UI**: токены VK/Max и ключ ИИ возвращаются в настройки только замаской (`••••1234`) — настоящее значение никогда не уходит в браузер, а неизменённая маска не перезаписывает сохранённый секрет.
- **Сессии**: смена пароля (в админ-панели или через `ADMIN_PASSWORD` в `.env` + перезапуск) и кнопка «Выйти» отзывают ранее выпущенные JWT — в токене хранится версия пароля, поэтому старый токен не действует остаток суток. Перезапуск с неизменным `.env` сессии не сбрасывает.
- **Fresh start**: при снятии с паузы или сохранении рабочих настроек история пропускается — в Max не выливается накопившийся бэклог.
- **Фильтры до ИИ**: минус-слова → обязательные ключевые слова → диапазон ER `(лайки + комменты×5 + репосты×10) / (просмотры + 2000) × 100`.
- **Промпт ИИ**: переписать/перевести/дайджест; маркер SKIP убирает пост из выдачи; при сбое ИИ — публикация оригинала (настраивается).
- **Медиа**: копирование фото/документов из VK в Max (до 10 вложений), ссылка на оригинал в сообщении. Если вложение не скачалось по сети или Max ответил 5xx — пост уходит в очередь и повторяется **вместе с медиа**; если файл удалён в VK или слишком большой (повтор не поможет) — текст публикуется, а событие и колокольчик получают явное «Вложения не прикреплены: …».
- **Наблюдаемость**: журнал потока (`Проверка запущена` → `Прогресс: N/M источников` → `Проверка завершена за X мин`), события с ER и статусом отправки, оповещения в колокольчике.
- **Безопасность лимитов VK**: глобальный троттлинг ~3 запроса/с, авто-пауза при flood-контроле/капче (в журнале видно `Пауза из-за лимитов VK`).
- **Несколько пользователей**: админ видит все потоки, пользователь — только свои.

## Как это работает

1. Поток запускается (или снимается с паузы) → сервис проходит по источникам и **фиксирует последние id постов** (история не публикуется).
2. Дальше отсчёт интервала от старта проверки; планировщик раз в ~30 с запускает проверки тех потоков, у которых интервал истёк (одновременно идёт только одна проверка). Если прогон длится дольше тика (поток с сотнями источников идёт минутами), следующие тики пропускаются — в журнале это видно строкой «Диспетчер: предыдущий прогон ещё выполняется — тик пропущен»; сам прогон не прерывается, а следующий стартует сразу после него.
3. Проверка собирает посты новее зафиксированных id, применяет фильтры и промпт ИИ.
4. Прошедшие посты публикуются в Max в хронологическом порядке, старт/итог проверки пишутся в журнал потока.

### Форматы списков

Поля «Источники VK», «Max каналы», «Ключевые слова» и «Минус слова» принимают **по одному значению на строку**.
При сохранении значения нормализуются: можно вставить список через запятую, точку с запятой или табуляцию
(а также текст с CRLF или даже с литеральными `\n`) — сервис приведёт его к виду «одна строка = одно значение».
Уже сохранённые «однострочные» списки исправляются автоматически при старте сервиса.

## Стек

- **Backend**: FastAPI, SQLAlchemy 2 (async), SQLite (WAL + `busy_timeout`), APScheduler, httpx, pydantic-settings.
- **Frontend**: React + TypeScript + Vite + Tailwind CSS (сборка уже лежит в `frontend/dist`).

## Структура

```
backend/               # FastAPI-приложение
  app/                 # api, сервисы (vk/max/ai), планировщик, модели
  run.py               # локальный запуск (uvicorn, 0.0.0.0:8000, reload)
  requirements.txt
  tests/               # самостоятельные тесты: python tests/test_*.py
frontend/              # SPA (src) + собранный dist/ (отдаётся бэкендом)
deploy/                # systemd-юнит, конфиг nginx, скрипт обновления
.env.example           # шаблон настроек → скопировать в .env
```

## Настройки (файл `.env` в корне проекта)

| Переменная | Обязательно | Описание |
|---|---|---|
| `SECRET_KEY` | да | Секрет для подписи JWT-токенов (длинная случайная строка) |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | да | Админ создаётся автоматически при первом старте |
| `VK_SERVICE_TOKEN` | да | Токен VK (сервисный или пользовательский) |
| `MAX_BOT_TOKEN` | да | Токен бота Max для отправки сообщений |
| `AI_PROVIDER` | нет | `gigachat` (по умолчанию) или `openai`-совместимый провайдер |
| `AI_API_KEY` | нет | Ключ ИИ (можно задать позже в «Настройках») |
| `AI_API_BASE` / `AI_MODEL` | нет | Адрес OpenAI-совместимого API и имя модели |
| `GIGACHAT_CREDENTIALS` / `GIGACHAT_SCOPE` / `GIGACHAT_MODEL` | нет | Для GigaChat напрямую |
| `MAX_NEW_POSTS_PER_RUN` | нет | Сколько новых постов забирать на источник за одну проверку (по умолчанию 200) |
| `MAX_RETRIES_PER_RUN` | нет | Сколько постов из очереди повторной отправки обрабатывать за прогон (по умолчанию 50) |
| `DATABASE_URL` | нет | По умолчанию `sqlite+aiosqlite:///./vk_alarm.db` |

> Токены VK/Max/ИИ можно задать и через интерфейс («Настройки») — они сохраняются в `.env`.
> `.env` в git не попадает (см. `.gitignore`).

## ИИ-провайдер (фильтрация и редактура)

Поддерживается любой OpenAI-совместимый API (`/chat/completions`) и GigaChat:

| Провайдер | Настройки |
|---|---|
| DeepSeek | `AI_PROVIDER=deepseek`, `AI_API_BASE=https://api.deepseek.com/v1`, `AI_MODEL=deepseek-flash`, `AI_API_KEY=...` |
| OpenAI-совместимый прокси/агрегатор | `AI_PROVIDER=openai` + свой `AI_API_BASE` / `AI_MODEL` / `AI_API_KEY` |
| GigaChat (Сбер) | `AI_PROVIDER=gigachat`, `GIGACHAT_CREDENTIALS=...` (опционально `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`) |

Заметки по эксплуатации:

- **DeepSeek из России работает без VPN** (проверено: `GET /v1/models` → 200, ответы 1–2 с). Быстрая проверка на сервере:
  ```bash
  curl -s -o /dev/null -w '%{http_code}  %{time_total}s\n' \
    https://api.deepseek.com/v1/models -H "Authorization: Bearer $AI_API_KEY"
  ```
  либо кнопкой «Проверить токен ИИ» на странице «Настройки».
- Сетевые сбои и лимиты (DNS, обрыв, 429/5xx) **ретраятся** (до 3 попыток с паузами), а после 3 сбоев подряд ИИ в текущем прогоне больше не дёргается. Сбои видны в журнале потока и в оповещениях: `ИИ недоступен: N пост(ов) — …`.
- Галочка **«Отправлять оригинал при ошибке ИИ»** в настройках потока: если включена, при недоступности ИИ пост уходит в Max без фильтра; для строгого отбора её лучше снять — тогда такие посты помечаются как «Отсеяно: ИИ» и не публикуются.
- Если промпт вернул маркер `SKIP` — пост не публикуется (растёт счётчик «ИИ отсеяно»).

## Локальный запуск

```bash
cd backend
python -m venv .venv
# Windows: .venv\Scripts\activate        Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

cp .env.example ../.env      # Windows: copy .env.example ..\.env
# заполните .env (SECRET_KEY, пароли, токены VK/Max)

python run.py                # http://127.0.0.1:8000
```

Фронтенд уже собран в `frontend/dist` и отдаётся бэкендом. Если меняли UI:

```bash
cd frontend
npm install
npm run build
```

Тесты (запускать как скрипты, не через pytest):

```bash
cd backend
python tests/test_er_and_filters.py
python tests/test_wall_pagination.py
python tests/test_max_service.py
```

## Запуск на сервере (Ubuntu/Debian)

Нужен VPS с Ubuntu 22.04/24.04 (или Debian 12), доступ по SSH и права `sudo`.
Понадобится ~250 МБ на диске (без Node.js). Node не нужен: собранный фронтенд уже в репозитории.

### Вариант 1 — одной командой (рекомендуется)

```bash
curl -fsSL https://raw.githubusercontent.com/Vepsnoid/vk-alarm-bot/main/deploy/install.sh | sudo bash
```

Скрипт сам: поставит пакеты, склонирует репозиторий в `/opt/vk-alarm-bot`, создаст venv и
установит зависимости, сделает `.env` из шаблона со случайным `SECRET_KEY`, выставит права,
поставит и запустит systemd-сервис `vk-alarm`, затем проверит `/api/health`.

После этого заполните настройки и перезапустите:

```bash
sudo nano /opt/vk-alarm-bot/.env      # ADMIN_USERNAME/ADMIN_PASSWORD, VK_SERVICE_TOKEN, MAX_BOT_TOKEN, ключ ИИ
sudo systemctl restart vk-alarm
curl http://127.0.0.1:8000/api/health
```

Интерфейс: `http://<IP-сервера>:8000` (или сразу настройте nginx/домен — см. ниже).

### Вариант 2 — пошагово

```bash
sudo apt update && sudo apt install -y python3-venv git nginx curl

sudo git clone https://github.com/Vepsnoid/vk-alarm-bot.git /opt/vk-alarm-bot
cd /opt/vk-alarm-bot

python3 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt

cp .env.example .env
nano .env                      # SECRET_KEY, ADMIN_*, VK_SERVICE_TOKEN, MAX_BOT_TOKEN, ключ ИИ

# сервис работает от www-data и должен писать базу в backend/
sudo chown -R www-data:www-data /opt/vk-alarm-bot
sudo git config --global --add safe.directory /opt/vk-alarm-bot   # чтобы sudo git pull не ругался

sudo cp deploy/vk-alarm.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vk-alarm
systemctl status vk-alarm --no-pager
curl http://127.0.0.1:8000/api/health      # ожидаем {"status":"ok", ...}
```

### Домен и HTTPS через nginx

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/vk-alarm
sudo nano /etc/nginx/sites-available/vk-alarm      # указать server_name (ваш домен)
sudo ln -s /etc/nginx/sites-available/vk-alarm /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx && sudo certbot --nginx
```

Файрвол (если включён `ufw`): `sudo ufw allow OpenSSH && sudo ufw allow 'Nginx Full'`.
Приложение слушает только `127.0.0.1:8000`, наружу его выставляет nginx — открывать порт 8000 не нужно.

### Проверка после установки

```bash
systemctl is-active vk-alarm                                  # active
curl -s http://127.0.0.1:8000/api/health                      # {"status":"ok",...}
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' \
  https://api.deepseek.com/v1/models -H "Authorization: Bearer $AI_API_KEY"   # 200 ... (если используете DeepSeek)
```

Дальше в интерфейсе: «Настройки» → «Проверить токен ИИ», создать поток, нажать ▶ и убедиться,
что в журнале потока есть `Проверка потока запущена` → `Проверка завершена за … мин`.

### Обновление версии на сервере

```bash
sudo /opt/vk-alarm-bot/deploy/deploy.sh
```

Скрипт делает `git pull`, обновляет зависимости и перезапускает сервис (фронтенд уже собран в репозитории;
если правите UI — соберите локально `npm run build`, закоммитьте `frontend/dist` и обновитесь).

### Перенос текущих данных с локального компьютера (по желанию)

Чтобы на сервере сразу были ваши потоки, события и логи — скопируйте базу (SQLite в режиме WAL,
поэтому нужны все три файла) при остановленном сервисе:

```bash
sudo systemctl stop vk-alarm
scp backend/vk_alarm.db backend/vk_alarm.db-wal backend/vk_alarm.db-shm user@server:/tmp/
ssh user@server 'sudo mv /tmp/vk_alarm.db* /opt/vk-alarm-bot/backend/ && sudo chown www-data:www-data /opt/vk-alarm-bot/backend/vk_alarm.db* && sudo systemctl start vk-alarm'
```

Пароль администратора и токены с локальной машины при этом не переносятся — они задаются в `.env` на сервере
(или логинитесь локальным админом, если в базе он уже есть).

## Эксплуатация: что важно знать

- **Один процесс.** Все защиты от параллельных запусков (блокировка проверок, очередь публикаций,
  глобальный троттлинг VK ~3 запроса/с) живут в памяти процесса, а база — SQLite. Поэтому сервис
  запускается без `--workers` и в одном экземпляре: второй процесс начнёт дублировать публикации и
  не будет видеть троттлинг первого.
- **Время.** В базе всё хранится в UTC, а интерфейс и фильтры по датам работают по московскому
  времени (UTC+3) — это осознанная настройка сервиса, а не автоопределение зоны.
- **Управление пользователями из консоли** (при недоступной панели):

  ```bash
  sudo -u www-data .venv/bin/python manage.py list-users
  sudo -u www-data .venv/bin/python manage.py set-password user1 new-pass   # отзывает токены
  sudo -u www-data .venv/bin/python manage.py set-role user1 admin          # отзывает токены
  sudo -u www-data .venv/bin/python manage.py delete-user user1             # потоки → админу
  ```

  CLI повторяет правила панели: смена пароля/роли отзывает ранее выданные JWT, последнего активного
  администратора нельзя понизить или удалить, а потоки удаляемого аккаунта переходят администратору.
- **Break-glass админ.** Логин из `ADMIN_USERNAME` — источник истины: при старте сервис синхронизирует
  его пароль и **возвращает аккаунту роль администратора и снимает блокировку** (в журнале это строка
  «Аккаунт '…' из .env восстановлен как активный администратор»). Поэтому `ADMIN_USERNAME`/`ADMIN_PASSWORD`
  в `.env` + перезапуск всегда дают рабочий вход в панель, даже если аккаунт по ошибке понизили или
  заблокировали. Неудачный запрос из панели (например, попытка админа снять роль с себя) `.env` не меняет:
  файл обновляется только после успешной записи в БД. Переименование этого логина из панели применяется
  сразу, без перезапуска сервиса (настройки читаются на каждый запрос).
- **Пароли.** Новые пароли длиннее 72 байт (лимит bcrypt) отклоняются с понятной ошибкой — и в панели,
  и в CLI. Legacy-записи, хранившие пароль открытым текстом, перехешируются на старте; если такой пароль
  был длиннее 72 байт, он мигрирует через предварительный SHA-256 (в журнале это видно отдельной строкой),
  поэтому вход полным паролем сохраняется — «хвост» пароля не отбрасывается.
- **Лимиты прогона** (`MAX_NEW_POSTS_PER_RUN`, `MAX_RETRIES_PER_RUN`) проверяются при старте: значение
  вне диапазона (1…10000 и 1…1000) или не число — сервис не запустится с понятной ошибкой, а не будет
  молча работать «как получилось».

## Данные и бэкапы

- База: `backend/vk_alarm.db` (SQLite). В режиме WAL рядом лежат `vk_alarm.db-wal` и `vk_alarm.db-shm` — при копировании берите все три файла (или остановите сервис).
- Секреты: только в `.env` на сервере, в git их нет.
- Логи systemd: `journalctl -u vk-alarm -f`.
